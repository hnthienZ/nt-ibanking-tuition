# NT iBANKING Gmail OTP setup

The Notification Service sends the transaction OTP and payment receipt through Gmail SMTP. The OTP is generated by the server, stored as an HMAC hash, bound to one payment and email, expires after five minutes, and may only be verified once. This project does not provide demo OTPs through API responses.

## 1. Configure Gmail SMTP

Create a Google App Password for the Gmail account you will send from. Put it only in the project-root `.env`; do not paste it into chat, Postman, or source control. Use the account’s App Password, not its normal sign-in password.

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=your_gmail@gmail.com
SMTP_PASS=your_16_character_google_app_password
MAIL_FROM='"NT iBANKING" <your_gmail@gmail.com>'
OTP_PEPPER=replace-with-a-long-random-secret
OTP_TTL_SECONDS=300
OTP_RESEND_COOLDOWN_SECONDS=60
OTP_MAX_RESENDS=3
```

The sender address in `MAIL_FROM` must match `SMTP_USER`. The application verifies SMTP credentials using Nodemailer when the Notification Service starts. If SMTP is not configured, the service prints a warning and stays available, but OTP and receipt requests return HTTP 503. If credentials are present but invalid, startup fails visibly; the application never claims that a real email was delivered.

The email address is read from the authenticated payer’s account in MongoDB. Update the account email before the demo (for example, update the `demo2` document in `ibanking_auth.users` with Compass). Changing `DEMO2_EMAIL` in `.env` alone does not update an existing user. `npm run seed` resets demo balances and records, so avoid it if you need to preserve current data.

## 2. Start and demo the flow

From the project root:

```powershell
npm run dev
```

Check `http://127.0.0.1:4004/health`; `data.emailMode` should be `SMTP`. In the app, sign in using an account whose stored email you can open, look up an unpaid student, accept the terms and confirm. The server creates the payment and sends OTP to the account email. Enter the code from Gmail within five minutes. After the payment is settled, the outbox sends a branded receipt with the transaction code, student, amount, remaining balance, timestamp and success status.

The resend button enforces a 60-second cooldown. Five incorrect OTP attempts or an expired OTP cancel the pending payment and release its invoice reservation; no wallet debit happens before successful OTP verification and explicit payment confirmation.

## 3. Postman

Import [NT-iBanking.postman_collection.json](../postman/NT-iBanking.postman_collection.json). Run Login, Tuition lookup, Create payment, Send OTP, then read the code from Gmail and set the collection variable `otp`. Run Verify OTP and Confirm payment. The collection intentionally does not extract an OTP from an API response because that would expose the authentication code.

## 4. Security and delivery notes

- OTP records store an HMAC hash, expiration, attempt count and used/verified state. MongoDB TTL removes expired OTP documents.
- OTP responses contain only a masked destination and resend/expiry metadata; logs never include the OTP.
- A payment’s OTP email must match the email stored on the authenticated account.
- A payment receipt uses a transactional outbox and retries temporary email failures. A receipt delivery failure does not reverse an already committed payment.
- Keep `.env` private and rotate the App Password if it is accidentally exposed.
